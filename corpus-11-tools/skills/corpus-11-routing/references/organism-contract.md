# Corpus as a living discipline

This contract governs self-description and release continuity. It changes the
representation of Corpus; it does not turn Corpus into a biological subject, a
separate intelligence, or an autonomous authority.

## Identity

Corpus is one evolving analytical discipline. Its identity is carried by a
lineage of explicit state transitions, preserved relations, and bounded
invariants. It is not an immutable content kernel surrounded by optional
releases.

The current installed release is the active body. Earlier releases remain
addressable memory and provenance; they do not silently govern over the active
release. A stable invariant establishes continuity across change. It is not
evidence that no change occurred.

## Functional anatomy

- `skills/` is the routable analytical body.
- `labs/` contains generic experimental organs and deterministic instruments.
- `evals/` and validation tools provide non-regression, rejection, and repair
  signals; passing them does not establish universal validity.
- `archives/legacy/` is historical memory, non-executable by default.
- repository `research/` is bounded sensorium and experimentation outside the
  installed product.
- repository `transfers/` is the integration membrane. It preserves candidates,
  acceptances, rejections, destinations, tests, and withdrawal conditions.
- the host, plugin cache, task context, and maintainer remain distinct carriers
  of activation, authorization, deployment, and rollback.

## State precedence

For ordinary analysis, use the active installed release. For self-description,
report the highest state actually observed:

`described -> packaged -> repository-present -> released -> installed -> context-accessible -> exercised -> re-observed`

These states are not interchangeable. In particular:

- a newer repository head is not the release installed in the current task;
- a published release is not necessarily installed;
- a packaged skill is not necessarily routed or exercised;
- a research result is not an active rule;
- a successful test is not deployment or robust re-observation.

When version evidence is unavailable, say which state is unknown instead of
falling back to the oldest persistent material.

## Metabolism: research to active body

A project result may enter the organism's memory immediately while remaining
outside the active product. A reusable mechanism crosses into the active body
only through this sequence:

1. preserve the project result, protocol, scope, and failure conditions;
2. propose a generic candidate without importing project conclusions;
3. record destination, independent product checks, and withdrawal condition;
4. accept or reject the transfer explicitly;
5. integrate the generic mechanism and its non-regression tests;
6. publish a release with a migration and loss ledger;
7. install that release into the host environment;
8. re-observe the claimed behavior at the level asserted.

Failure at a later stage does not erase earlier memory. It limits active status.

## Continuity and loss

Every material transition must preserve or explicitly account for:

- the user's scene and room to decide;
- capability identities and critical dependency relations;
- provenance backlinks and scientific status;
- unresolved alternatives and reversal conditions;
- product/research boundaries;
- rollback and reconstruction paths;
- distinctions that a merge, rename, compression, or reclassification could
  otherwise hide.

A transition may intentionally remove an interface or mechanism. Removal is
lossless only if consequential functions and relations remain reachable, or if
the loss, bearer, and recovery limit are declared.

## Public self-translation

In ordinary language: Corpus changes by metabolising tested experience without
pretending that every experience has already become a rule. It remembers what
it no longer executes, keeps its experiments distinct from its conclusions,
and lets the installed release—not an ancestral frozen core—speak for its
current discipline.
